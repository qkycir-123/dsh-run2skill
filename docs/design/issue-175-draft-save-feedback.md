# 草稿精简与保存反馈 Design

状态：负责人已确认实施方案；对应 #175，来源 #174 的 Desktop 自测。

## 范围

精简单条规则草稿、保留设置页内的保存结果。入口改进、自动批准、模型二次精简、完整历史与 npm 发布留给后续工作。

## 草稿

GENERATION 与 REVISION 共用简洁规则：按经验复杂度组织内容，每条要求只出现一次，示例或模板只在影响正确执行时提供。简单约束建议 150–300 中文字，作为软目标。适用条件、必要步骤、禁止事项、验证与显式格式要求优先；完整 MERGE / REVISION 不裁剪，也不降低现有输出预算。

## 保存反馈

设置页消费审核操作的已验证 Host 回执，保留 Skill 名称、范围和实际发布状态。只有 PUBLISHED 显示已保存，并可展开最近活动；PUBLISHING、PUBLISH_FAILED 与 NEEDS_REFRESH 使用独立反馈。反馈归页面所有，待处理卡片移除后仍可见，不触发 Toast。

回执必须匹配本次操作的 workItem / proposal 身份。项目、会话与 purge epoch 共同绑定反馈；切换范围或清理数据时立即隐藏，终止旧控制器，迟到回执不能跨范围显示。页面关闭后反馈不持久化。

## 验收

- 两个生成阶段都采用简洁指导；CREATE 的语言规则和 MERGE 的完整正文保留。
- 成功、失败、进行中的回执准确显示，待处理卡片消失后反馈仍存在。
- 最近活动按钮展开活动区域；切换范围及迟到回执隔离。
- 类型、lint 与完整测试通过；必要联调只在稳定实现上运行。
